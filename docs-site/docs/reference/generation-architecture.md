## What it is

JobOps currently has several related generation features, but it does not yet have one generic generation framework.

The main areas are:

| Area | Output | Lifecycle |
| --- | --- | --- |
| Job scoring | Suitability score and structured job brief | Generated during scoring and stored on the job |
| Resume tailoring | Headline, summary, skills, experience selection/bullets, and project selection | Generated before PDF rendering and stored on the job |
| Resume rendering | Job-specific PDF | Generated file with freshness and regeneration tracking |
| Application kit | Readiness view over existing job fields and artifacts | Computed in the client; not stored as its own object |
| Ghostwriter | Conversational drafts | Stored as job chat messages |
| Resume Studio AI | Individual resume-field suggestions | Ephemeral until the user applies them |
| Job documents | User-uploaded supporting files | Stored attachments; not generated by JobOps |

The current resume path can be read as:

```text
Job import
  -> scoring and job brief
  -> resume tailoring
  -> optional experience role selection and bullet consolidation
  -> project selection
  -> persist job-specific resume fields
  -> compose a resume document
  -> render through Reactive Resume, LaTeX, or Typst
  -> save a scoped PDF
  -> fingerprint the inputs
  -> expose the result in the application kit
```

## Why it exists

This documentation separates the current responsibilities before new output types such as cover letters, application answers, interview packs, or outreach messages are added.

The important distinction is:

- CV generation is a backend generation and artifact lifecycle.
- The application kit is currently a frontend composition of existing data.
- Ghostwriter and uploaded documents are adjacent features, not part of the CV pipeline.

Keeping those boundaries clear helps avoid putting every new generator inside the resume-specific `generateFinalPdf()` flow.

### Main code boundaries

| Layer | Responsibility | Main locations |
| --- | --- | --- |
| Client workflow | Starts generation and displays readiness | `orchestrator/src/client/pages/orchestrator/JobDetailPanel.tsx`, `orchestrator/src/client/api/jobs.ts` |
| API | Validates tailoring, PDF, and document requests | `orchestrator/src/server/api/routes/jobs/documents.ts` |
| Orchestration | Coordinates tailoring, rendering, status, usage, and conflicts | `orchestrator/src/server/pipeline/orchestrator.ts` |
| LLM abstraction | Resolves provider/model, prompt templates, and structured-output behavior | `orchestrator/src/server/services/modelSelection.ts`, `orchestrator/src/server/services/experience-tailoring.ts`, `orchestrator/src/server/services/llm/` |
| Persistence | Stores job fields, artifact metadata, and scoped files | `orchestrator/src/server/repositories/`, `orchestrator/src/server/services/*-storage.ts` |

## Common problems

### The job brief is described as CV tailoring

The brief is produced during scoring. Resume tailoring separately uses the job description and profile.

### The application kit is described as a generated backend object

There is no application-kit table, service, or API aggregate today. The client computes it from job fields.

### Ghostwriter is described as the generic generator

Ghostwriter is conversational and message-oriented. It does not provide deterministic artifact fingerprints, stale-state tracking, or regeneration lifecycle.
